## 2. 目标架构与范围

```text
学校系统 ← Rust 会话与受控请求 ← 宿主能力调度 ← 隔离模块
               ↑                    ↑
           设备内 Cookie       签名清单 ∩ 原生上限 ∩ 用户授权

学生认证上游 → Casdoor → App / 外部应用 → Mini 后端业务 API
                         ↑                     ↑
                     标准登录链路          应用权限 ∩ 用户授权

审核清单 → 接入程序 → Casdoor 配置 / 数据策略 / 签名应用目录
审核后的模块产物 → 发布签名 → CDN → Rust 验证后加载
```

学校会话和 Casdoor 会话各自管理。统一登录暂不可用，不应阻断仍然有效的学校本地业务和离线缓存；需要云端身份的功能应明确显示不可用原因。

### 2.1 应用分三类

- **第一方模块**：经审核并签名，按登记能力调用本地学校会话。更新页面和解析规则，不替换主壳与验签器。
- **成员或第三方模块**：默认无学校会话权限，无 Cookie 导出、主令牌、桥令牌和任意 IPC 权限。首期只开放业务级最小能力；完成跨平台隔离验证之前不开放通用学校请求。
- **独立网页/有后端应用**：通过 Casdoor 建立自己的会话，以面向指定资源的令牌调用 Mini 后端。App 主令牌不得直接交给成员应用；静态网页无后端不意味着必须继承宿主全部身份。

身份令牌、模块发布签名、本地桥凭据和游戏 Launch Ticket 是四种不同的凭据，不互相替代。现有游戏结算的服务端凭据链保持独立验收。

### 2.2 本期交付边界

- 交付模块运行时安全基础、一个真实只读模块闭环、统一应用目录、Casdoor 验证与分阶段迁移方案。
- 首个模块以已掌握协议的只读学校接口为样本；R8 的两家新接口待输入后再接入，不猜测其协议或鉴权。
- 默认复用现有应用中心与宿主视图。独立桌面窗口作为产品后续项，不把现有未调用的函数当作已上线能力。
- 主壳继续正式更新；本期不建设整包热更激活器。旧实验入口在替代方案验收后另行停用或清理。
- 不把“成绩课表全部上传 NAS”当隐含前提；端侧读取和云端数据共享分别规划。

## 3. 必须落实的技术契约

### 3.1 本地桥与模块容器

1. `Protected` 路由不得仅凭 Origin/Referer 放行。主壳优先通过原生调用；确需 HTTP 的宿主请求持有进程内桥凭据，令牌只通过受保护原生通道交给宿主，不出现在 URL、日志、模块存储或子页面中。
2. 区分静态模块资源、图书馆官方页代理、本机 Agent 只读接口、调试接口和宿主业务接口。逐类限制，避免取消一条来源规则后扩大其他路由的访问。
3. 模块内容使用与业务 API 分离的来源，并限制资源路径；容器采用最小 sandbox、导航和下载权限。换端口和 sandbox 是组合措施，均不单独视为权限认证。
4. 宿主消息校验窗口来源、实例、协议版本、请求 ID 和能力。每次 remount、导航、退出或账号切换后失效。opaque origin 不全局放行，使用绑定已知子窗口的专用握手通道，不向通配目标广播凭据。
5. 验证模块无法绕过消息通道直接调用 Tauri IPC、HTTP 桥、本地数据库或凭据接口。Linux/Android 的 iframe 与主窗口 IPC 边界存在平台限制，需原生实测；不能证明隔离的平台，成员模块不授予本地敏感能力。
6. Android 当前远端 iframe 属于单独的加载通道。带本地权限的模块必须最终执行经过 Rust 验证的固定产物及依赖；首期不得通过直接远端导航绕过该要求。跨端可信加载方案未通过时，只允许无本地能力的网页或正式包内模块。

### 3.2 受控请求与数据能力

内部原语可采用 `session_fetch`，对模块暴露可审核的能力标识和受限参数；模块自行声明的 ID、学号、权限不是授权依据。

- Rust 精确限制 host、端口、规范化路径、方法及可用会话；不接受任意完整 URL、用户信息段、任意代理目标或无限制 headers。
- 自动携带对应学校 Jar；禁止模块自带或读取 Cookie、Host、会话认证头；对响应剔除 Set-Cookie 等凭据字段。
- URL 和每次重定向都校验目标，超时、请求/响应体积、并发与调用频率均有上限；TLS 兼容只能沿用指定学校域的既有策略。
- 有效权限取“原生固定上限、已验证清单权限、当前用户授权、当前模块实例和账号会话”的交集。Rust 执行最终检查，宿主 JS 校验用于提前提示。
- 自动续期通过现有 session guard；写请求不因重登、超时而盲目重放。首个模块只读。
- 账号切换立即作废旧实例授权、在途结果和敏感缓存，防止 A 账号的数据返回到 B 的界面。
- 第一方模块可按登记能力获取必要原始响应并在 JS 解析；成员模块首期优先取得有限业务数据，不能共享整套通用网络权限。

### 3.3 模块更新与签名

- Rust 内置受信公钥，校验清单规范化字节的 Ed25519 签名。签名覆盖 module ID、版本/发布序号、渠道、包摘要、入口、原生/桥协议兼容范围、权限及可执行依赖。
- 清单和包分开验证：有签名才能接受包摘要；缺签名、缺摘要、未知 key ID、字段被改写均拒绝。所有可执行脚本受验证，不能从签名 HTML 再加载任意远端脚本绕过校验。
- 验签后下载、验摘要、安全解包、检查入口，再原子激活；设置压缩包体积、解压总量、文件数和路径边界。缓存命中不能绕过签名或账号/版本规则。
- 安装包持有信任根；发布签名不使用普通开发者随意可取的密钥。构建与上传 CI 可运行，签名步骤在独立受控签名环境完成；若密钥在线，则明确其真实信任边界，不称为离线私钥。
- 防版本回放，并保留受控回退：本机已知良好版本可按固定回退规则恢复；远端降版需显式受信发布决定，不接受 CDN 直接回放旧清单。
- 定义签名密钥和模块版本的撤销机制、策略有效期及离线规则；密钥轮换由现有信任根授权，不能让远程配置自行添加公钥。离线不能承诺即时获知撤销，敏感新能力在策略过期时拒绝。
- 启动后台检查目录和更新；未打开的模块下次打开生效，正在运行的实例固定当前版本。失败继续使用已验证兼容版本，主壳启动不阻塞。
- 已有 11 个第一方游戏需重新签名并回归后加入新通道；不以“旧包兼容”给未签名远端代码开放敏感权限。

### 3.4 Casdoor、学生认证与数据授权

- 先在测试应用固定实际部署镜像摘要，再验证 PKCE/native client、学号 claim、组权限、已登录账号绑定、关闭注册时的上游建号、设备流程及令牌交换。
- token exchange 必须证明源令牌、交换调用方和目标 audience 的关系合法，并拒绝无目标应用权限的用户。若不支持当前设想，则保留标准 OIDC 授权码流程；不把 App 主令牌转发给第三方，也不在 public App 内置 client secret。
- device grant 须验证 App 凭据能否实际完成批准、批准界面、拒绝/取消、过期和轮询；有端点或元数据声明不视为流程验收通过。
- Cookie 一次性服务端核验作为候选路线，依赖学校网络可达性、跨 IP 可用性以及对原隐私承诺的正式处理。未解决前不开放学生自动建号；普通客户端模块工作可独立继续。
- 如采用此路线，只传必要教务 Cookie，固定校验地址，禁用不受控跳转，不落库、不进任何链路日志；结果绑定一次性认证事务。密码不上传；失败不得降级为自报学号。
- 新绑定使用经过核验的学校身份；旧 `verification_level=low` 不自动升级。已有成员账号需要证明两侧身份再绑定；重复/冲突记录隔离处理。
- 初期不重写论坛等现有业务主键。维护 `(issuer, sub)`、内部用户、已核验学校身份和旧用户记录的映射，逐项对账；账号注销重建等情况不能仅凭相同学号静默承接资产。
- 资源服务器按 issuer 分别固定 JWKS、audience、算法和 claim 映射；token 的 `aud` 标识接收资源，调用客户端的标识来源另行确定，不能无条件把两者混为一项。
- 管理权限用固定、可验证的 Casdoor group/role 映射，定义撤权生效期限。旧 Identity JWT、Casdoor JWT、论坛 legacy HMAC 是三条分别观测和退出的路径；坏 JWT 不降级。
- Mini 数据访问取“应用获批数据域、用户有效同意、操作类型、数据归属”的交集；授权扩容重新同意，支持拒绝和撤销。
- 学校数据默认仍在设备；模块在设备内取数。云端应用若要读学校数据，需要额外定义用户主动同步/定向分享、来源时间、过期和删除；不依赖已计划退役的境外快照，不将学校 Cookie分发给应用。

### 3.5 清单接入与平台差异

- 审核清单登记应用 ID、负责人、形态、入口、模块签名产物、兼容范围、请求权限、数据域及用途、Casdoor client/回调与可登录组。
- 接入程序先创建不可用应用，完成身份权限、业务策略、签名目录和部署检查后再启用。部分失败不允许形成整个组织默认可登录的应用；提供幂等、对账、撤销和 secret 轮换。
- 目录可以来自 NAS，静态包继续用 CDN；未签名远程配置只能影响展示和已有开关，不能扩张原生权限、替换信任根或授权执行新代码。
- 商店版与其他分发版明确列出模块、原生桥、数据共享及更新能力。评审条款未完成前，新增带学校原生能力的远程模块不扩展到商店版；原有会话开关也需检查，不将“真实登录后放开”作为审核豁免。
- 没有桥、协议不兼容或验证未通过的平台显示清晰降级：无敏感能力网页、包内功能或提示正式更新，不静默失效、不自动转发凭据。

## 5. 验证方式与发布门槛

本轮未运行测试或构建。实施时优先补真实行为的正反用例，避免只检索源码字符串的“通过”。

- 桥授权单元/集成用例：无Origin、伪造Referer、任意loopback端口、模块同源、opaque origin、无令牌/错令牌、公共路由和官方预约代理。
- 模块运行用例：直接fetch桥、直接invoke、伪造模块ID、重放消息、导航/remount、账号切换、旧缓存、离线、坏签名、恶意ZIP、远端脚本与Android远端入口绕过。
- 请求用例：编码路径绕过、跨域跳转、Cookie/Authorization注入、超大响应、会话过期、非幂等写入重试、并发登出。
- 身份用例：伪造学号、跨事务批准、重复/冲突绑定、issuer/kid串用、错误aud、scope缺失、group撤销、坏JWT降级、HMAC签发旁路、跨用户数据读写。
- 使用现有客户端门禁：`npm run typecheck`、相关 `vitest`、`npm run test:bridge-compat`、`npm run test:more-module-bridge`、`npm run build`；Rust按改动模块运行测试与静态检查。既有脚本不能代替原生WebView实测。
- 每次测试进程设置最多60秒的超时，超时记录为未通过并拆分；需更长的构建使用单独构建作业，不把超时当成功。
- macOS/iOS 构建与设备测试交给对应平台；Windows上的类型检查或浏览器模拟不能标记为三端已验收。
- 生产指标分别记录各issuer认证、legacy HMAC使用、认证失败、模块验签/回退和业务错误；不记录Cookie、token、handoff和学生敏感原文。

## 6. 发布前决策与默认假设

这些事项当前不要求暂停规划；没有证据时保持关闭相应新能力，继续独立任务。

1. **学校身份核验**：Cookie是否跨IP可用、NAS是否可达、隐私承诺如何变更。未解决则不开放学生批量自动注册，也不回退自报身份。
2. **Casdoor兼容性**：以部署镜像的实际行为为准；exchange/device不通过时保留标准OIDC可用流程，不提前删除旧入口所需代码。
3. **平台能力**：统一接口不等于相同权限。Android/iOS安全加载与IPC隔离没有实测证据时，第三方敏感模块保持不可用。
4. **两家新接口**：尚无名称、域名、协议、鉴权和数据说明。先做现有只读样本，不为未知服务提前开放任意host。
5. **业务数据与用户规模**：执行前统计实际用户、设备、应用和旧token类型。未核对的历史身份不自动授予可信身份或关联敏感资产。
6. **签名保管**：发布负责人决定实际签名环境与轮换方式。默认不把发布私钥交给普通Web门户或成员仓库CI。
7. **商店版**：本期不承诺通过通用原生桥热更新所有iOS功能。按实际功能、公开审核要求与分发渠道验收，不能依据演示账号路径推定全量合规。

## 7. 回退与旧平台退役条件

- 客户端新能力默认可单独关闭；模块失败回到已验证兼容包或包内功能，不能回退到允许模块直接取Cookie的路径。
- 认证灰度按账号/客户端版本控制，旧JWT与HMAC分别设置有限兼容窗口；不能通过重开无鉴权签发或自声明绑定来实现回滚。
- 业务数据库尽量保留现有键，新增映射先旁路验证再启用；对账前不重写历史归属。发现冲突只隔离涉及记录，不批量猜测修复。
- 退役需有：账号映射对账、必要重新核验、第三方迁移确认、旧凭据使用量观察、撤权/登出演练、所有支持平台验收和恢复操作记录。
- T14结束前完成全范围预退役审查。T15先做可恢复停用与观察；实际删库、删除快照、注销凭据等动作仍须按明确范围另行授权，不因排进任务表就自动执行。
- 境外快照删除、数据库下线、旧域名放弃及实验热更代码清理作为单独列明范围的变更。现阶段仅规划，不执行删除；旧域名可先保留迁移提示和回调观察，不继续承接高风险旧认证。
- 最终关闭顺序：停止高风险旧签发 → 完成新链路灰度 → 结束安全兼容窗口并拒收旧凭据 → 停旧服务 → 按既定保留策略处理数据与基础设施。
