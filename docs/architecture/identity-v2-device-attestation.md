## 1. 需求方定的约束（本方案的前提，不可绕开）

| # | 约束 | 对方案的后果 |
|---|---|---|
| C1 | **不改隐私/威胁模型承诺**：学校 cookie 不上传云端 | ❌ 排除 FDL §3 的"教务 cookie 一次性校验" |
| C2 | **NAS 连不到教务**（网络不可达） | ❌ 同上，服务端无法自行核验学生身份 |
| C3 | **本机 App（Tauri）是教务的唯一入口，也是教务数据的唯一出口** | ✅ 身份声明只能由 App 产出，且必须**可验证来源** |
| C4 | **用设备签名；设备登记与验签放在 ocr-service** | ✅ 信任根 = 设备密钥 + 服务端设备登记表 |
| C5 | 新组件放**新仓库** | ✅ `superdaobo/mini-hbut-student-auth` |
| C6 | **先做调试接口**，漏洞（本地桥）延后 | ✅ 阶段 0 = 调试接口；桥安全列"成员应用进模块中心前必做" |

**FDL 已定且本方案照做的部分**（不因 C1/C2 改变）：
- **Casdoor 是唯一签发方**；mini App 与成员小应用**直接对 Casdoor 做 OIDC**；
- **ocr-service 是资源服务器**（验 Casdoor 令牌），不再建号、不再签断言、不再发令牌；
- **学生身份核验是 Casdoor 的"上游 OIDC 提供方"形态**（本方案把它的证据源从教务 cookie 换成设备签名）；
- **高权限（管理员）由 FDL 在 Casdoor 群组里手动给**，后端只读令牌里的 `groups`；
- 应用接入走**清单仓库 + PR 审核 + NAS 接入程序**；
- 过渡期 **ocr-service 支持双 issuer**。

## 2. 目标架构

```
┌────────────────────────────────────────────────────────────┐
│ App（Tauri）= 教务唯一入口 / 教务数据唯一出口                 │
│ · 设备私钥（keyring，service=mini-hbut-identity，永不外传）  │
│ · 登录教务后本地已知 学号/姓名/院系                            │
│ · 签名声明：canonical(学号|姓名摘要|device_id|nonce|ts)       │
└───────────────┬────────────────────────────────────────────┘
                │ ① 设备签名声明（deep link minihbut:// 或本机桥）
┌───────────────▼────────────────────────────────────────────┐
│ 学生认证服务（新仓 mini-hbut-student-auth，NAS 上）           │
│ · 角色：Casdoor 的**上游 OIDC 提供方**（type=OIDC）           │
│ · 端点：discovery / authorize / token / jwks + /health       │
│ · 不连教务、不收 cookie、不存密码                              │
│ · 身份依据：设备签名 → 调 ocr-service 验签/查登记              │
└───────────────┬────────────────────────────────────────────┘
                │ ② 内部 API（http://fdl-ocr-service:7860，内网）
┌───────────────▼────────────────────────────────────────────┐
│ ocr-service                                                 │
│ · 设备登记表（学号↔设备唯一绑定）+ 验签 + 限流 + 审计 + 吊销    │
│ · 资源服务器：验 Casdoor 令牌（iss/jwks/aud/exp）+ 读 groups   │
└───────────────┬────────────────────────────────────────────┘
                │ ③ id_token（sub=学号 或 hbut_<学号>，含 hbut_student_id）
┌───────────────▼────────────────────────────────────────────┐
│ Casdoor（sso.hbut.site）= 唯一签发方                          │
│ 幂等建号/绑定 → AT/RT/ID；权限 perm-<app>-<群组>              │
└────────────────────────────────────────────────────────────┘
```

**信任链**：`设备私钥` → `学生认证服务验签` → `ocr-service 登记与绑定` → `Casdoor 上游登录` → `Casdoor 令牌` → `资源服务器验签`。

## 3. 设备签名的能力边界（必须让所有人看见）

### 3.1 能证明
- 该请求**确实由持有 `device_id` 对应私钥的那台设备**发出（签名不可伪造、不可重放到超过时间窗）；
- 该 `(学号, 设备)` 组合**在服务端登记过**，且**没有第二个设备占用同一学号**；
- 该身份声明**自首次登记以来未被静默改写**（学号↔姓名/院系一致性）；
- 全流程**可审计、可吊销**（谁在什么时候用哪台设备登记/换机）。

### 3.2 不能证明（**残余风险，明文接受**）
- **不能证明"这个人真是这个学号"**：只有 App 能看到教务，服务器看不到；`(学号, 设备)` 的首次绑定**谁先登记谁占有**。
- 因此本方案**不把"学号"当作授权依据**：高权限一律走 Casdoor 群组（FDL 手动给），冒领者最多得到普通学生权限。

### 3.3 与 FDL 记录的旧漏洞的关系
FDL 2026-10-31 指出：旧设备签名链路里 `enroll` 是公开接口 + handoff 易得 ⇒ "脚本就能以任意学号注册或挂到别人身份上"，并建议整套退役。
本方案**不是**恢复那套：
| 旧链路的缺陷 | 本方案的对策 |
|---|---|
| enroll 公开、无凭据 | 登记必须带**设备签名**且经**限流**（阶段 1）；登记入口不对外匿名开放（阶段 2 由上游流程驱动） |
| 新设备可直接接管既有学号（#679） | **换设备必须旧设备批准或人工**（恢复 threat-model §3 的"禁止自动接管"） |
| 设备签名即身份（无绑定） | **学号↔设备唯一绑定 + 一致性审计 + 吊销** |
| 论坛管理员按学号自动给 | **管理员改由 FDL 在 Casdoor 群组手动给** |

**结论**：本方案把"任意冒领"压缩到"**抢先占用**"，并把冒领的收益压到"普通学生权限"，同时留下审计痕迹。**风险下降但不归零**，这一点不掩饰。

## 4. 分阶段（阶段 0 先行）

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| **0** | **调试接口**：新服务 `/debug/*`、ocr `/identity/debug/device/*`、App DEV 签名自检缝 | 本机 `tauri dev` + 新服务 + ocr-service + 假 Casdoor **四方跑通**，贴真实输出 |
| 1 | 设备登记与验签（ocr-service）：设备表、唯一绑定、换机批准、限流、审计、吊销 | 单测 + 契约测试 + 绑定/换机/冒领（被拒）三类用例 |
| 2 | 学生认证服务（新仓）：OIDC 上游端点 + 设备核验 + 联调 | discovery 正确；Casdoor 配好上游后可完成一次登录 |
| 3 | ocr-service 退化为资源服务器：退役建号/断言/bootstrap；双 issuer；白名单数据授权；groups；CORS 收紧；`/health` 轻量 | 全量测试绿 + 过渡期双 issuer 验证 + 回滚演练 |
| 4 | 客户端：Casdoor 授权码+PKCE；会话交 refresh token；退役设备换票（legacy 开关） | 首次登录/换设备/退出/切号 全部通过 |
| 5 | 清单仓库 + 接入程序；退役 identity-platform 注册表/门户 | 一个示例应用经清单 PR 全自动接入 |
| 6 | 实测与验收（自测）：Casdoor 5 项 + 端到端矩阵 + 回滚演练 | 验收矩阵全绿 |
| **延后** | 本地桥安全（`127.0.0.1` 任意端口可信 + iframe 无 sandbox）；测试应用/空名应用清理 | **成员小应用进模块中心之前必须完成** |

## 5. 不变式（迁移期间必须保持）

1. **密码不出设备**（沿用）；**cookie 不上传**（C1 沿用）；
2. **设备私钥不出设备**（keyring，不可用即 fail closed，不降级）；
3. **JWT 验签失败不降级 legacy**；
4. **过渡期双 issuer 并行**，新链路全绿前不动旧链路；
5. **会断线的操作只在 03:00–05:59**（FDL 维护窗口）；
6. 任何写操作（Casdoor 配置、NAS compose/env、DNS、Vercel/Neon 下线）**先经需求方或 FDL 确认**。

## 6. 与 FDL 三份标准的对应

| FDL 要求 | 本方案落地 |
|---|---|
| Casdoor 唯一签发方；应用自接 OIDC | 阶段 4（客户端）+ 阶段 5（成员应用） |
| ocr-service 只做资源服务器 | 阶段 3 |
| 学生核验=上游登录方式 | 阶段 2（**证据源改为设备签名**，理由见 §1 C1/C2） |
| 数据授权不靠 scope，靠 `client_id→数据域` 白名单 | 阶段 3 |
| 高权限走 Casdoor 群组、读 `groups` | 阶段 3 |
| 应用接入=清单+PR+接入程序 | 阶段 5 |
| 双 issuer 过渡 | 阶段 3 |
| `/health` 轻量、`/api/v1/`、无宿主端口、secrets 只读挂载 | 阶段 0/2/3 |

## 7. 未验证 / 待实测（不得当成已完成）

1. Casdoor 侧 5 项：登录页 device grant 二维码入口；token exchange 是否检查应用权限；**Token attributes 能否把学号改名成 `hbut_student_id`**；已有账号绑定上游的行为；关闭注册时上游新用户能否建号。
2. 上游 OIDC 提供方在 Casdoor 4.20 的配置形态（字段、回调、`oauth_OIDC_id` 的写入行为）。
3. 设备密钥的算法与现有 keyring 里的类型是否一致（Ed25519/ES256）；签名 canonical 串与既有实现是否冲突。
4. NAS 上以什么身份跑"学生认证服务"（容器名、网络、Traefik 路由、资源上限）——需 FDL 定。
5. `mini.hbut.site` 线路 A/B 与可达性（与身份链路相关但不阻塞阶段 0/1）。
